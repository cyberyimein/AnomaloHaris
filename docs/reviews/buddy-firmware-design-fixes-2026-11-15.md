# Buddy 0.5.0 设计整改与实机验收

本记录对应 [0.4.7 设计审查](buddy-firmware-design-audit-2026-11-15.md)。原审查与复现脚本保留为历史基线，当前回归以 `firmware/stackchan/test_*.py` 和服务端测试为准。

## 整改结果

| 项目 | 当前行为 |
| --- | --- |
| F1 网页方向操作 | 只发送 `head.move`，拍照是独立操作；保留明确的转向并观察组合能力。 |
| F2 同步阻塞 | 非阻塞 socket、总收发期限、分块写入；收发间继续服务触摸、电源、灯光。LCD 绘制延后并合并最新状态，舵机命令先于耗时绘制发送。 |
| F3 动作确认 | 返回实测姿态及目标姿态，3° 误差限、动作期限；缺失反馈或不到位返回失败并安全断开舵机电源。 |
| F4 关机回复依赖 | 接受关机后设置 2500ms 后备期限；正常回包后缩短到 500ms，回包失败不撤销关机。 |
| F5 只读副作用 | 状态、触摸、电源等只读调用不进入动作表现，不撤销手动灯光。 |
| F6 故障生命周期 | 持久化组件故障与单次参数/调用错误分开；成功验证对应组件恢复后才清除故障。网页显示故障。 |
| F7 图像时间 | 像素归属明确后、相机释放前记录设备单调时间；接收与处理时间分别记录，无法换算的绝对采集时间保持 null。 |
| F8 扩展输入约束 | 主机使用 Ajv；设备使用明确支持的 schema 子集并拒绝不支持的定义，handler 之前检查。 |

## 实机发现与修正

- 相机用实体文字目标确认默认水平镜像；每次初始化后调用 `set_hmirror(False)`，保留按次初始化、像素复制、释放和屏幕恢复，避免共享缓冲重新引入混图。
- 原生相机初始化约 276ms、采集约 74ms、像素复制约 29ms。主要延迟并非传感器曝光：LCD 首次状态绘制实测约 930ms，缓存帧约 217ms。传输期间反复刷新 LCD 会累积明显卡顿，因此收发期间延后 LCD、继续处理输入和灯光。
- 实装 SDK 的扭矩反馈必须读地址 40 的一个字节；其 `read_torque_enable` 读 word，会把开启返回为 256。
- 实装设备对目标寄存器的写入会使扭矩变为开启：`write_pos`、`write_word(42, pos)`、`gen_write(42, ...)` 均经 byte40 回读确认。释放头部必须完全避免同步目标。恢复保持/移动仅同步为刚测得的当前位置，再验证开启状态；不更改 EEPROM 限位或 NVS 标定。
- Wi-Fi 在支持时关闭省电，与旧 Arduino 的 `WiFi.setSleep(false)` 对齐；单独禁用省电未测得稳定提速，不作为性能收益依据。
- 热路径中的局部 `import time` 在实装 UIFlow 上每次约 67ms；十次时钟辅助函数调用实测约 675–676ms。模块初始化时导入后复用，避免每次触摸与生命周期轮询重复导入。
- 204800 字符的 base64 图像通过通用 `ujson.dumps` 编码单次约 3.8 秒；原生 base64 往返校验约 246ms。图像专用 JSON 路径需先验证尺寸、数据长度及 canonical base64，元数据继续使用通用 JSON 编码，不采用占位符替换。
- 服务状态探测超时从 1500ms 调整到 4000ms，避免原生绘制期间的短暂延迟造成误报离线；动作期限单独保留。

## 验证边界

设备仍是协作式单线程：原生 LCD、相机和部分 I2C 调用无法被 Python 中途抢占。慢连接期间的持续轮询不等于硬实时保证。软件屏幕截图表示已提交帧，不是物理 LCD 回读。

旧固件的 25° 回中与当前 45° 尚未更改；应结合机体摆放与视线决定。录音、触摸滑动等扩展能力留在后续能力开发范围，不把灯光的 listening 表现当成已有录音能力。

固件 0.5.0、Buddy Service 和前端已部署到内网设备及 Mac mini；旧容器保持停止状态，未删除，便于回退。配置、设备 token 与 NVS 舵机零点未修改。
